# Document processing and RAG research

Reviewed: 2 October 2026; Docling/HNSW and task-specific structured-output lookup updated 4 October 2026. Sources below are primary documentation or papers; LangGraph documentation was also queried through Context7. This records the approved direction and supporting research, not a benchmark report. Implementation is in progress; actual parser/model/retrieval and UI results belong in the living implementation plan. Current documentation can change, so implementation must resolve and record dependency/model versions. The current manifests select LangGraph 1.x and OpenAI Python SDK 2.x; a declared version range is not an installed-version verification.

## Recommended baseline

Use **Docling for structured conversion and selective OCR, Docling HybridChunker, PostgreSQL full-text search plus pgvector, LangGraph for workflow orchestration, and OpenRouter for generation and embeddings through the OpenAI Python SDK**. Use RQ/Redis for background job transport, with SQL-owned durable records. Measure parsing quality, retrieval recall, answer support, latency, and cost separately.

The main efficiency gains should come from avoiding repeated work: parse once, retain source locations, reuse unchanged embeddings, batch embedding requests, retrieve relevant evidence, and cache only when per-message source versions and conversation context match. These are engineering choices, not performance claims from the sources. No whole-document extracted-token cap, fixed evidence-token ceiling, or maximum chat/comparison selection count is part of the current design; model input/context limits are still checked and overflow is handled visibly.

## Findings and decisions

| Technique | What the evidence supports | Decision for DocVault |
|---|---|---|
| Structured conversion | Docling has a unified representation for text, tables, hierarchy, and provenance. [Document model](https://docling-project.github.io/docling/concepts/docling_document/) | Preserve the structured artifact and source locations; avoid a plain-text-only intermediate. |
| Selective OCR | Docling offers native-text and OCR controls, including region selection; full-page OCR is a distinct, more expensive path. [Pipeline options](https://docling-project.github.io/docling/reference/pipeline_options/), [OCR example](https://docling-project.github.io/docling/_generated/examples/full_page_ocr/) | Start with the standard pipeline and selective OCR. Benchmark clean, scanned, and mixed PDFs. Do not force OCR on every page. |
| Structure-aware chunking | Docling's HybridChunker combines document hierarchy with token limits and supports repeated table headers. [Chunking](https://docling-project.github.io/docling/concepts/chunking/) | Use the installed HybridChunker with OpenAITokenizer/tiktoken and a 600-token contextualized input budget. Let Docling split/merge structured items and repeat table headers. The application retains provenance and explicitly serializes picture text for OCR; TXT uses a structured adapter. |
| Image text in chunks | OCR text nested under picture items needs explicit serialization consideration. [Serialization example](https://docling-project.github.io/docling/_generated/examples/advanced_chunking_and_serialization/) | Include a scan/image-text fixture; confirm extracted text actually reaches chunks. Parser success alone is insufficient. |
| Hybrid retrieval | pgvector documents combining vector search with PostgreSQL full-text search and reciprocal rank fusion (RRF). [Hybrid search](https://github.com/pgvector/pgvector#hybrid-search) | Use both semantic and lexical candidates. PostgreSQL `ts_rank_cd` is the lexical baseline; do not describe it as BM25. |
| Contextual retrieval | Anthropic describes generating explanatory context per chunk and using it in dense and BM25 retrieval, optionally with reranking. Its reported gains apply to its evaluation setup. [Contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | Begin with deterministic title/heading prefixes. Evaluate generated context only if ambiguous chunks cause measured retrieval failures. Do not assume published gains transfer. |
| Filtered vector search | Approximate nearest-neighbor filtering can underfill results; pgvector documents iterative scans and exact-search alternatives. [Filtering](https://github.com/pgvector/pgvector#filtering) | Use native cosine HNSW with `m=32`, `ef_construction=200`; transaction-local `ef_search=200` and `iterative_scan=strict_order` require pgvector 0.8+. Retain PostgreSQL GIN/full-text and RRF. Verify EXPLAIN index use and filtered recall; leave tiny-scope planner choices to PostgreSQL. |
| Structured generation | OpenRouter accepts `response_format` JSON Schema on compatible provider endpoints and supports structured streaming; compatibility is endpoint-specific. [Structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) | Pass Pydantic `ChatGenerationLLMResponse {response, suggestions, citation_ids, outcome}` and analysis models directly to the installed SDK parse/stream helpers; the SDK generates the strict schema and validates final output. Native Pydantic partial JSON parsing handles provisional response strings. At most three suggestions; use `require_parameters: true` and verify the actual endpoint. Schema compliance does not establish factual correctness. |
| Embedding reuse | OpenRouter provides `/embeddings` and array inputs, including `openai/text-embedding-3-small`. [Embeddings](https://openrouter.ai/docs/api_reference/embeddings), [Model](https://openrouter.ai/openai/text-embedding-3-small) | Call via the OpenAI SDK against OpenRouter. Verify 1,536 output dimensions before using `vector(1536)`. Batch within verified input/request limits; cache exact input/model/configuration and preserve provenance when splitting oversized inputs. |
| Native usage accounting | OpenRouter returns native input/output counts, optional cached/reasoning details and cost automatically; streams report usage in the final SSE message. Legacy request flags are deprecated. Embeddings return input/total usage. [Usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting), [embedding response](https://openrouter.ai/docs/api/api-reference/embeddings/submit-an-embedding-request) | Record input/output/cached tokens and cost when supplied. Preserve missing values as unknown, including streams interrupted before terminal usage. Current storage omits separate total/reasoning/cache-write/audio/upstream-cost fields; reconciliation is pending. |
| Provider prompt caching | Cache behavior depends on the model/provider route and must be verified for the configured endpoint. [OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching) | Keep stable instructions and schemas first. Record cached tokens when reported; do not assume a discount or cache hit. This is distinct from local completed-answer reuse. |
| Real streaming | OpenRouter sends incremental generation and may report errors after a stream has started; abort support varies by upstream provider. [Streaming](https://openrouter.ai/docs/api_reference/streaming) | Forward actual response-text deltas via Python SSE; validate/persist before final completion. Handle usage frames and midstream errors, fence cancelled attempts, and do not equate disconnection with zero billing. |
| Workflow orchestration | LangGraph models steps, conditional routing, and invocation state; its persistence features depend on a checkpointer. [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | Compile ingestion/chat/analysis graphs around small functions. SQL remains authoritative for messages, jobs, and application checkpoints; defer a LangGraph checkpointer and make no automatic graph-resume claim. |

The HNSW parameters are application tuning choices, not pgvector defaults. The 4 October synthetic filtered-neighbor investigation found inadequate recall with `m=16`/`ef_construction=64`; increasing query breadth alone did not resolve it. The selected `m=32`/`ef_construction=200`/`ef_search=200` improves the index graph and query recall at the cost of more index memory, construction work and search work. Keep a real-corpus recall/latency gate; a passing synthetic nearest-neighbor check does not establish document-answer quality or production capacity.

## Alternatives evaluated

| Option | Useful when | Tradeoff and disposition |
|---|---|---|
| `pdfplumber` / `pypdf` plus `python-docx` | Mostly clean, simple, digital documents | Smaller baseline; more responsibility for reading order, tables, OCR routing, and source mapping. Use as a benchmark control or an explicit fallback if Docling misses the deployment budget. Do not maintain two full ingestion stacks without evidence. |
| Mistral Document AI | Complex scans or layouts justify managed OCR | Current APIs expose structured OCR, table options, locations, and confidence information. Adds a provider, data transfer, credentials, and usage cost. Keep as a measured fallback candidate, not a default dependency. [OCR documentation](https://docs.mistral.ai/studio/document-processing/basic_ocr) |
| MinerU | More demanding self-hosted document parsing | Current research includes efficient vision-language parsing and subsequent data-centric improvements. Hardware, operational footprint, and dependency fit need measurement. Defer for this backend assignment. [MinerU2.5](https://arxiv.org/abs/2509.22186), [MinerU2.5-Pro](https://arxiv.org/abs/2604.04771) |
| Late chunking | Long-range context is lost by independent chunk embeddings | Applies chunk pooling after long-context token encoding. It requires an appropriate embedding path; it is not achieved by changing an OpenAI embedding request's chunk size. Defer unless the baseline fails contextual retrieval cases. [Paper](https://arxiv.org/abs/2409.04701) |
| ColPali / visual retrieval | Answers depend heavily on charts, diagrams, or page layout | Retrieves using page-image representations. Adds a different index and inference path; it does not by itself produce grounded answers. Defer unless visual question answering becomes a requirement. [Paper](https://arxiv.org/abs/2407.01449) |

No autonomous tool-use loop, GraphRAG, or separate vector service is needed. The user selected LangGraph for explicit workflow orchestration. Use ordinary Python functions for conversion, retrieval, model calls, validation, and persistence; graph nodes coordinate these functions without hiding selected-source filtering or citations. PostgreSQL loads conversation history for each invocation. RQ re-delivers durable application jobs; the graph reuses SQL stage outputs. This provides application-managed recovery, not automatic recovery of transient LangGraph state.

## Model and queue choices

- **Provider client:** OpenAI Python SDK with `base_url="https://openrouter.ai/api/v1"` and server-side `OPENROUTER_API_KEY`. Use the OpenRouter Chat Completions and embeddings interfaces. The SDK choice does not mean requests go directly to OpenAI. [OpenRouter SDK configuration](https://openrouter.ai/docs/quickstart)
- **Task models:** independent configurations for chat, rewriting, summaries and comparisons in `llm/config.py`; shared templates in `llm/prompts.py`. Repository defaults use [GPT-4.1 Nano](https://openrouter.ai/openai/gpt-4.1-nano) for rewriting, [GPT-4.1 Mini](https://openrouter.ai/openai/gpt-4.1-mini) for chat/summaries and [GPT-4.1](https://openrouter.ai/openai/gpt-4.1) for comparisons. These are configurable initial choices; comparative quality/cost evaluation is pending. User-local chat configuration is preserved.
- **SDK parsing:** inspected installed OpenAI Python **2.54.0** and Pydantic **2.13.5**, with official SDK docs queried through Context7. `chat.completions.parse(response_format=Model)` and `stream(response_format=Model)` derive strict schemas and parse final Pydantic models; SDK context managers close streams. Read available response-envelope usage before parsing can reject content. [SDK helpers](https://github.com/openai/openai-python/blob/main/helpers.md), [raw responses](https://github.com/openai/openai-python#accessing-raw-response-data-eg-headers)
- **Partial text:** the installed SDK partial parser waits for a string to close. Use `pydantic_core.from_json(..., allow_partial="trailing-strings")` on SDK snapshots for actual unfinished answer-text deltas; full SDK model validation remains mandatory. This replaces custom key scanning, escape/surrogate decoding and schema normalization. [Pydantic JSON parsing](https://docs.pydantic.dev/latest/concepts/json/), [core parser options](https://docs.pydantic.dev/latest/api/pydantic_core/#pydantic_core.from_json)
- **Embeddings:** `openai/text-embedding-3-small`, expecting 1,536 dimensions and requiring a live response check. A dimension/model change requires a separate index generation and compatible query/document embeddings. Never silently truncate an embedding input or mix dimensions.
- **Queue:** RQ + Redis fits ordinary Python task functions and the existing planned dispatcher. Application idempotency, leases, checkpoints, and unique active-work claims still protect writes/external calls. Choose one retry owner rather than layering uncontrolled SDK, graph, and queue retries. [RQ jobs](https://python-rq.org/docs/), [Retries](https://python-rq.org/docs/exceptions/)
- **BullMQ:** Python bindings exist. RQ is selected for the compact Python implementation and current job contracts, not because BullMQ is Node-only. [BullMQ Python](https://docs.bullmq.io/python/introduction)
- **Frontend:** React/Vite/assistant-ui/shadcn talks directly to FastAPI JSON and SSE. The user requested assistant-ui on 2 October 2026; installed `@assistant-ui/react` 0.15.23 uses [External Store Runtime](https://www.assistant-ui.com/docs/runtimes/custom/external-store) to adapt existing history and generation callbacks. [Component primitives](https://www.assistant-ui.com/components) provide the thread/composer without changing Python persistence or the source/citation contracts. Official docs were read and queried through Context7; installed package types/source confirmed the runtime and callback APIs. The browser renders response deltas, suggestions, and resolved citations; it does not need an additional Node LLM proxy. The approved local shared-workspace scope has no IAM/key-entry UI.
- **Persistence:** compile graphs without a checkpointer initially. SQL-owned sessions, immutable per-message source snapshots, generation state, and ingestion stage outputs avoid two competing persistence authorities. Introduce a checkpointer only with a deliberate later migration of ownership, if resumable graph features become necessary.

## Experiments before tuning

1. Parse a clean PDF, two-column PDF, table PDF, scan, mixed scan/text PDF, DOCX, and TXT. Inspect extracted text, order, table relations, source locations, missing pages, runtime, and peak memory. Include a chart-only question expected to be unsupported.
2. Compare a plain token-split/dense baseline with structure-aware chunks, then hybrid retrieval. Use the same evidence-labeled questions and model settings.
3. Sweep chunk budgets of 400/600/900 tokens on the tuning set; count heading prefixes and table headers in the actual budget. Evaluate retrieval before evaluating generation.
4. Add reranking only if retrieval errors remain. Compare its recall benefit, latency, and cost against the simpler pipeline; retain it only if it meets the stated budget.
5. Benchmark warm and cold parser starts separately. Pin OCR dependencies/model assets so the demo does not download models on its first upload.
6. Verify exact-cache hits, changed-selection/version/history misses, deleted-source invalidation, and explicit regeneration bypass. Record provider calls avoided rather than inventing dollar savings. IAM and cross-workspace isolation are deferred.
7. Exercise large documents and selections beyond the removed arbitrary caps. Verify per-request model safety and explicit overflow behavior without silent truncation or dropping required sources.
8. Verify SQL history across independent sessions and graph re-invocations, plus cancel/late-result fencing and regeneration after completion. Real OpenRouter structured deltas and usage are a separate smoke from deterministic provider fixtures.

The acceptance corpus and proposed release gates are in [the specification](spec.md); the experiment order is in [the implementation plan](implementation-plan.md).
